## 2. Task 2 — wave-2/3 module skeleton, wired without editing a shared file

### 2.1 What the brief asked, and what I did instead (with evidence)

The brief asked for `pub mod core;` etc. **in `src/lib.rs`**. Taken literally that is
unbuildable: a `mod` declaration needs its file, so `src/lib.rs` would refuse to compile until
waves 2 *and* 3 *and* the platform/conformance waves had all written their module file — and the
first agent to land would force the rest to edit `src/lib.rs` to move from an inline placeholder
to a file declaration. That is precisely the conflict the brief is trying to prevent.

So the declarations are emitted by `build.rs` into `OUT_DIR/smart_lib_modules.rs` (which
`src/lib.rs` already `include!`s — unchanged since 01), with exactly the same
exists-or-placeholder rule the domain modules use:

* the owner writes `src/core/mod.rs` (or `src/core.rs`, or `src/platforms/<os>.rs`) →
  build.rs emits `#[path = "<abs>"] pub mod core;` — **that file is the whole wiring step**;
* nobody has written it → build.rs emits a documented empty module, which compiles with
  nothing in it, satisfying the no_std requirement trivially.

`src/lib.rs`'s doc block documents the pattern (and that `domains` is already emitted the same
way). Nothing in `src/lib.rs` changed for this task; the equivalent content is in the generated
tree.

### 2.2 The generated tree, as emitted for the default feature set

This was not a design claim — it happened while I was writing the report:

### 2.4 `platforms` design note

## 3. Task 3 — the OUT_DIR inventory (one artifact for codegen and conformance)

### 3.1 What build.rs now emits

Two artifacts in `OUT_DIR`, plus the existing `triad.txt` and the module tree:

| artifact | env var at crate compile time | content |
|---|---|---|
| `codegeneratorrequest.bin` | `SMART_LIB_CODEGEN_REQUEST` | the raw CodeGeneratorRequest capnpc just consumed (a capnp message; read it with `capnp::schema_capnp::code_generator_request::Reader`) |
| `codegen-inventory.txt` | `SMART_LIB_CODEGEN_INVENTORY` | the text index rendered *from those bytes* (format in §3.3) |

Both are set with `cargo::rustc-env=…`, so `src/conformance/**` (and tests) can reach them at
compile time with `env!(...)`. Nothing else changed about codegen: the same
`capnpc::CompilerCommand` still produces the Rust, it is simply told to keep the request
(`.raw_code_generator_request_path(...)`) instead of discarding it.

This is exactly what `knowledge/03-CONFORMANCE.md` §9 asks for ("expose the compiled
CodeGeneratorRequest … so the generator and the codegen share one artifact"), and it answers
§2.1's verdict (introspection, not schema-parse) with the compiler's own bytes rather than a
second parser of schema source.

### 3.2 Two defences against the artifact silently lying

1. **Identity assertion.** build.rs panics if the request's `requested_files` is not exactly the
   compiled set:

   ```
   build.rs: the CodeGeneratorRequest does not describe the compiled set.
      compiled (7): abi.capnp audio.capnp capability.capnp files.capnp network.capnp system.capnp types.capnp
      requested by the compiler (…): …
   ```

2. **A build-time self-check.** Every rendered inventory is verified against itself before it
   is written: `schema` lines == `summary schemas`, the per-file `structs`/`enums`/
   `interfaces`/`methodStructs`/`consts` counts sum to the summary's values, `interface` and
   `method` line counts equal the summary's, no unknown line kind appears, and every
   interface's ordinals are contiguous `0..n-1` (validator rule E13). Any mismatch panics the
   build. This is why tests are not the only guard: the artifact cannot be written while it is
   inconsistent, in any configuration, including ones nobody runs tests in.

   It earned its keep immediately: it caught that the summary's `methodStructs` counted only
   the compiler's `$Results` structs while the per-file lines reported params + results
   (summary 218 vs per-file 335 for the default set). Both are now 335 + the 218 void-result
   gap is a documented capnp fact, not a bug.

3. **Traversal-budget bug found and fixed (this is the interesting one).** The first
   implementation looked up interface nodes by re-scanning the node list for each lookup, and
   capnp's reader spends a *traversal budget* on every pointer dereference. After ~600 lookups
   the budget ran out and `get_nodes()` started returning `ReadLimitExceeded`; the code path
   swallowed the error and the inventory silently omitted the last 5 interfaces of the default
   set (28 claimed, 23 listed; `network.capnp` lost `NicProvider`, `StatusSubscription`,
   `TelemetrySubscription`; `system.capnp` lost both). Fixed by indexing the node list once
   (`BTreeMap<u64, node::Reader>`) and looking up from the map; the lookup failures are now
   `panic!`s rather than silent `continue`s. The test asserts
   `interface lines == summary interfaces == 303/28/…` so this class of bug cannot come back.

### 3.3 The inventory format (documented in the artifact's own header)

```
# smart-lib codegen inventory (v1) -- GENERATED by build.rs, DO NOT EDIT.
# Derived from the CodeGeneratorRequest build.rs feeds to capnpc: the SAME artifact that
# generates the Rust under test, never a second parse of schema source. Regenerated on every
# build; byte-identical for a given feature set (no timestamps, no absolute paths, fixed sort
# order) -- L0 determinism is asserted by building twice and diffing.
# Triad: binary Cap'n Proto version 1.4.0 | codegen capnpc 0.27.0 | runtime capnp 0.27.2
#
# Line grammar (whitespace-separated fields):
#   schema  <file> id=<hex> module=<mod> kind=<foundation|domain> feature=<name|none> structs=<n> enums=<n> interfaces=<n> methodStructs=<n> consts=<n>
#   interface <file>:<Iface> methods=<n>
#   method <ordinal> <methodName> interface=<file>:<Iface> params=<n> results=<n> flags=<csv|->
#     flags, in this fixed order, present only when the shape matches:
#       capability    a parameter typed capability.capnp:Capability
#       dataHandleIn  a parameter typed types.capnp:DataHandle
#       dataHandleOut a result typed types.capnp:DataHandle
#       errorOut      a result carrying a types.capnp:Error arm
#       listOut       a result field typed List(_)
#       noParams      the parameter struct declares no fields
#       pagination    a parameter typed types.capnp:Pagination
#   summary <key>=<n> ...   totals over exactly the compiled set, for diffing against the
#     contract's own measurement.
```

Worked excerpt (real output, default feature set):

```
schema files.capnp id=0xa1b2c3d4e5f60025 module=files_capnp kind=domain feature=domain-files structs=141 enums=13 interfaces=4 methodStructs=217 consts=0
interface files.capnp:Files methods=74
method 0 openFile interface=files.capnp:Files params=2 results=1 flags=-
method 2 readFile interface=files.capnp:Files params=3 results=1 flags=dataHandleOut
method 5 listDirectory interface=files.capnp:Files params=2 results=2 flags=listOut,pagination
method 73 unlockFile interface=files.capnp:Files params=1 results=1 flags=-
```

Notes that matter to readers:

* **Node attribution** is the compiler's own display-name prefix, so a domain lists only its own
  surface even though the request carries the transitive import closure (`shell` compiling
  emits 13 schema lines but attributes only its own nodes; `compositor` types are counted under
  `compositor`).
* **`methodStructs`** is the compiler's synthetic `<iface>.<method>$Params/$Results` count,
  kept apart from the schema's own structs.
* **Ordinals are the compiler's `code_order`** — the value the contract promises never moves,
  which is why L1's ordinal-stability regression lock can be generated from this file alone.
* **Well-known types are resolved from the node set itself** (`capability.capnp:Capability`,
  `types.capnp:{Pagination,DataHandle,Error}`), so a contract-side id change cannot desynchronise
  the flags from the code.
* Flags descend into nested groups and into `List(...)` element types, so a capability or a
  pagination buried in a group is still reported.

## 3.7 Finding: `--all-features` cannot build the library on this machine — and that is the charter's law, with a number on it

```
$ time cargo build -j 6 --all-features
… 89 schemas compiled, inventory written …
error: process didn't exit successfully: rustc --crate-name smart_lib … --cfg 'feature="domain-access"' … (signal: 9, SIGKILL: kill)
real 13m4.030s
$ free -m    # 15,704 MB total, ~6.8 GB available
```

The lib rustc was OOM-killed while compiling the union of all 89 schemas' generated code
(~125 MB of generated Rust in one crate). `cargo check --all-features` survives (metadata only,
8.7 s) and compiles everything except the in-flight transport file. So:

* **`--all-features` is a build-graph/codegen integrity check, not a shippable configuration.**
  It is now proven to work for the *codegen* half (89/89 schemas, 303 interfaces, 3,143 methods,
  deterministic artifacts) and to fail at the *lib* half from memory, on a 15 GB machine.
* **Do not put `--all-features` in CI as a build step.** Use it (or the matrix in §1.3) as the
  feature-law audit; ship per-feature-set builds. Note that even `cargo check --all-features`
  can OOM when several agents build in the workspace at once (observed: a later `check` run was
  rustc-killed while the same command had succeeded minutes earlier), so an all-features audit
  should run on a quiet machine or with `-j 2`.
* This is charter law #2 with evidence: "never compile all 88 domains at once — that is the
  failure mode this law exists to prevent." I am not proposing a workaround (e.g. splitting the
  crate per domain) — that is an orchestrator decision, §7 request 3.

## 4. What later waves must know

1. **`src/lib.rs` is frozen for you.** Adding a domain = your file + one manifest line (the
   wire agent's). Adding `core`/`transport`/`platforms`/`conformance` = writing your module file.
   Neither edits `src/lib.rs`.
2. **`#[path]`-based registration means your file's own `mod` declarations resolve normally**:
   `src/core/mod.rs` declaring `pub mod error;` finds `src/core/error.rs`.
3. **Read the inventory, not the schemas, for the method surface.**
   `env!("SMART_LIB_CODEGEN_INVENTORY")` for the text index, `env!("SMART_LIB_CODEGEN_REQUEST")`
   for the raw request. The L0 determinism, the L1 method-totality and ordinal-stability locks,
   and the L2 shape rules all key off those two files; the shape flags are already computed.
4. **capnp 0.27 API reminders** (unchanged from 01, worth repeating): `init_root::<T::Builder<'_>>()`,
   per-type modules (`types_capnp::timestamp::Reader`), enums at module scope
   (`capability_capnp::Operation::Read`), generated `Server` traits are **not** dyn-compatible
   (RPITIT) — plan `dyn` only at the transport seam (law #4).
5. **The `std` feature is a widening switch only**; the core stays no_std (law #1). `no
   `extern crate alloc` in a hand-written module means no `format!`/`Vec` — that is the
   shape of the errors waves 2/3 are currently fixing in their files.
