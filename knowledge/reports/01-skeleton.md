How the triad actually works (this is the important detail): capnpc 0.27.0 is a **pure-Rust
code generator**. It runs `capnp compile -o- …` on the installed C++ binary, reads the raw code
generator request from stdout, and generates Rust in-process. So the version coupling is
through the request format, not through a linked library.

**Verdict: compatible, no error to report.** Binary 1.4.0 + capnpc 0.27.0 generate and compile
all four pilot domains plus the transitive-import experiments below (kernel, shell) with zero
errors. The generated files themselves declare the versions they were produced by:

```
// capnp binary version: 1.4.0
// capnpc crate version: 0.27.0
```

One triad detail later waves must know: capnp's capability machinery (`FromClientHook`,

## 5. Decisions a later wave must know

**D1 — comments must be stripped before parsing imports.** `usb.capnp`'s prose names the
deleted `filesystem.capnp`; a naive `import "` match would make the build fail on a deleted
schema that nothing imports. `src/codegen/mod.rs::strip_capnp_comments` runs before
`imported_schema_files`.

**D2 — generated file layout is a flat list of `pub mod <type> { … }` blocks, *not* wrapped in
a module named after the file.** The wrapper module (`crate::schema::types_capnp`) is ours;
capnp 0.27 only emits per-type modules at file scope. This is why the injected `alloc` imports
land inside the first item of each type module, and why `default_parent_module(["schema"])`
is the only way cross-file references resolve.

**D3 — capnp 0.27 API shape differs from 0.25.** `init_root::<T::Builder<'_>>()`,
`get_root::<T::Reader<'_>>()` (not `::Owned`); structs/structs-of-structs are reached through
a per-type module (`capability_capnp::capability::Reader`); enums are at module scope with
CamelCase variants (`capability_capnp::Operation::Read`); generated `Server` traits are **not**
dyn-compatible (RPITIT methods) — do not plan `dyn …::Server` in transport seams; use the
generated `Client`/`Params`/`Results` types.

**D4 — `include!`-based registration means domain code compiles *inside* `pub mod domains`,
not as a sibling of lib.rs items.** A domain module addresses its schema as
`crate::schema::<stem>_capnp::…` (no `self::` shortcuts through the crate root, and no
`use crate::schema::…` ambiguity).

**D5 — the `std` feature is a widening switch, not a behavioural one.** Core stays no_std even
with `std` on, per law #1.

**D6 — why `#[allow(unused_imports)]` matters for CI.** 2,281 warnings from the old
un-post-processed port would break any `-D warnings` CI. Now: one informational warning line.

#### API sketch for Wave 2 (`src/core/**`) — law #3, law #6
The generated interface traits are not dyn-compatible and their `Server` methods are
async-shaped, so core should wrap, not re-export, them:

```rust
/// Per-domain trait (one object-safe trait per domain; NO god-trait).
pub trait FilesBackend {                     // src/core/files.rs (wave-2 agent's file)
    fn caps(&self) -> DomainCaps;            // law #6: every backend publishes caps()
    fn open(&self, req: files_capnp::open_request::Reader<'_>) -> OpenOutcome;
}

/// Law #6: honest degradation is a first-class result, not an error state.
pub enum OpenOutcome { Opened(FileHandle), Unavailable(UnavailableReason) }
pub struct UnavailableReason { pub code: UnavailableCode, pub detail: Text }   // Text = alloc::string::String

/// Law #5: authority is a handle — no permission strings anywhere.
pub struct Authority(capability_capnp::capability::Owned);   // opaque; never parsed
```

#### API sketch for Wave 3 (`src/transport/**`) — law #4
One `Channel` shape over InProcess / Shmem / UnixSocket / Tcp; `dyn` belongs here and nowhere
else, and only at the seam:

```rust
pub trait Channel: Send {
    fn send_frame(&self, frame: &[u8]) -> Result<(), TransportError>;   // bounded, no polling
    fn recv_frame<'b>(&self, buf: &'b mut Vec<u8>) -> Result<&'b [u8], TransportError>;
    fn caps(&self) -> TransportCaps;      // capability-transfer semantics, declared per transport
}
pub enum Transport { InProcess, Shmem, UnixSocket, Tcp }
```

These sketches are suggestions only — `src/core/**`, `src/transport/**`, `src/domains/**`,
`src/platforms/**` and `src/conformance/**` were **not** created by this brief.

## 6. Note for the conformance agent
The generated tree is deterministic per feature set, so generated conformance tests can be
driven off the same closure: `codegen::modules::render_module_tree` and the schema-set resolver
in `build.rs` are the single source of truth for "what is compiled". Two cheap entry points for
a generated conformance harness:

* `crate::schema::<stem>_capnp::introspect()` — capnp exposes a schema introspect API per
  generated type, which is enough to assert, e.g. that every union arm other than the
  terminator is exercised;
* `enum_list`/`struct_list` readers round-trip through `capnp::serialize`, which is what
  `tests/smoke.rs` already uses — the same trick scales to a table-driven generator.

## 7. Lessons (also appended to `knowledge/lessons/01-skeleton.md`)
* capnp 0.27 crisply separates: `capnpc` (codegen, pure Rust) from `capnp` (runtime). The
  installed C++ binary is only the schema compiler front-end; the version people normally worry
  about is the *request format*, which worked with 1.4.0 without complaint.
* Post-processing generated code is a codegen-output concern, not a dependency concern: keeping
  it in `src/codegen/**` and including it from both `build.rs` and a test target gave it
  mechanical tests for the cost of one `#[path]`.
* Comments in a schema tree are load-bearing *data* (they name deleted files). Strip, then parse.
* `#[path]` inside an inline module resolves relative to that module's directory, not the
  file's; emitting absolute paths from build.rs avoids the whole class of bug.
